### Цель проекта
Построить модель, предсказывающую отток клиентов банка (`churn`), чтобы банк мог приоритизировать клиентов с высоким риском ухода и направлять им целевые предложения (скидки, персональные условия) — вместо того, чтобы обращаться ко всем клиентам без разбора.

**Задача** : 
бинарная классификация (churn: 1 = ушёл, 0 = остался).

**Данные:**  набор данных банковского оттока клиентов с Kaggle.
10 000 клиентов банка, признаки — кредитный рейтинг, страна, пол, возраст, стаж обслуживания, баланс, количество продуктов, наличие кредитной карты, статус активности, предполагаемая зарплата. Дисбаланс классов: ~80% / ~20%.

### Метрика успеха:
Основная — `F1-мера` 

Дополнительная — `ROC-AUC / PR-AUC`

**Scope v1:**
- Обучение на всех доступных данных без дополнительной фильтрации по клиентам
- Сравнение моделей от простых к сложным: логистическая регрессия → SVM → случайный лес → бустинг
- Интерпретация через SHAP — **отложена** на следующую итерацию
- Деплой (FastAPI + Docker) — **отложен** на следующую итерацию

# Iteration 1

## Результаты

### Сравнение моделей

Все модели обучены с учётом дисбаланса классов (~80/20) через `class_weight="balanced"`
(для XGBoost — `scale_pos_weight`). Метрики посчитаны на отложенной test-выборке (30%,
stratified split), порог классификации — 0.5 (дефолтный, единый для всех моделей для
честного сравнения).

| Модель | F1-score | ROC-AUC |
|---|---|---|
| Logistic Regression | 0.518 | 0.792 |
| SVM (RBF kernel) | 0.602 | 0.865 |
| Random Forest | 0.639 | 0.872 |
| **XGBoost** | **0.647** | 0.870 |

### Выбор финальной модели

**XGBoost** — лучший результат по основной метрике (F1). Random Forest показывает
практически идентичное качество (разница в пределах шума), но XGBoost выбран как
основная модель для дальнейшей работы.

### Feature engineering

В пайплайн добавлены два признака:
- `balance_per_product` — баланс, приходящийся на один продукт клиента (вовлечённость
  в продукты банка)
- `balance_per_tenure` — темп накопления баланса относительно стажа обслуживания
  (`balance / (tenure + 1)`)

Также был протестирован бинарный признак `has_balance` (флаг наличия ненулевого
баланса, выделяющий клиентов без депозита) — эмпирически не дал значимого прироста
метрик для XGBoost и был исключён из финального пайплайна.

### Известные ограничения / открытые вопросы

- **`active_member`** — признак потенциально может нести временную утечку (неясно,
  зафиксирован ли статус активности до или после решения клиента уйти; в данных нет
  временных меток для проверки). Признак оставлен в модели. Проверка через SHAP/feature
  importance — следующая итерация.
- **SHAP-анализ** (полный, по всем признакам) — отложен на следующую итерацию.
- **Деплой** (FastAPI + Docker) — отложен на следующую итерацию.
