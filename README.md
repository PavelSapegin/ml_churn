### Цель проекта
Построить модель, предсказывающую отток клиентов банка (`churn`), чтобы банк мог приоритизировать клиентов с высоким риском ухода и направлять им целевые предложения (скидки, персональные условия) — вместо того, чтобы обращаться ко всем клиентам без разбора.

**Задача** : 
бинарная классификация (churn: 1 = ушёл, 0 = остался).

**Данные:**  набор данных банковского оттока клиентов с Kaggle.
10 000 клиентов банка, признаки — кредитный рейтинг, страна, пол, возраст, стаж обслуживания, баланс, количество продуктов, наличие кредитной карты, статус активности, предполагаемая зарплата. Дисбаланс классов: ~80% / ~20%.

### Метрика успеха:
Основная — `F1-мера` 

Дополнительная — `ROC-AUC / PR-AUC`

**Scope v1:**
- Обучение на всех доступных данных без дополнительной фильтрации по клиентам
- Сравнение моделей от простых к сложным: логистическая регрессия → SVM → случайный лес → бустинг
- Интерпретация через SHAP — **отложена** на следующую итерацию
- Деплой (FastAPI + Docker) — **отложен** на следующую итерацию

**Известные риски / точки для проверки:**
- Признак `active_member` потенциально может нести временную утечку (не удалось
  подтвердить это через корреляцию — leakage проверяется по причинности, а не силе связи).
  Решение: оставить в модели, перепроверить важность через SHAP после обучения.ls




## Результаты первой операции

### Методология обучения и валидации

Данные разбиты на три части: **train (56%) / val (14%) / test (30%)** — стратифицированное
разбиение в два этапа (`train_test_split` со `stratify` дважды), чтобы сохранить
исходное соотношение классов (~80/20) в каждой части.

Гиперпараметры Random Forest и XGBoost подбирались через **Optuna** (50 итераций):
модели обучались на `train`, оценивались на `val` — `test` в процессе подбора не
участвовал. Для этого использован отдельный трансформер (`transformer_tuning`),
обученный (`fit`) только на `train`.

После выбора лучших гиперпараметров финальные модели (включая Logistic Regression и
SVM, без тюнинга) обучены на `train + val` вместе (`X_full_train`, 70% данных) с
помощью отдельного трансформера (`transformer_final`), обученного на этом же объёме.
`test` использовался только один раз — для финальной оценки, той же шкалой
(`transformer_final`), что и обучение.

### Сравнение моделей

| Модель | F1-score | ROC-AUC |
|---|---|---|
| Logistic Regression | 0.518 | 0.792 |
| SVM (RBF kernel) | 0.602 | 0.865 |
| **Random Forest (тюнинг Optuna)** | **0.647** | 0.868 |
| XGBoost (тюнинг Optuna) | 0.632 | 0.868 |

Все модели обучены с учётом дисбаланса классов через `class_weight="balanced"`
(для XGBoost — `scale_pos_weight`). Метрики — на отложенном `test`, порог
классификации 0.5 (единый для всех моделей).

### Выбор финальной модели

**Random Forest** — лучший результат по основной метрике (F1). Изначально по
метрикам лидировал XGBoost, но при более честной схеме валидации (train/val/test
вместо прямого сравнения на test) и после расширения диапазона Optuna-поиска для
XGBoost (`max_depth` до 15) Random Forest стабильно показывает более высокий F1 при
сопоставимом ROC-AUC. Разница в ROC-AUC между RF и XGBoost (0.868 vs 0.868) в
пределах шума.

### Feature engineering

В пайплайн добавлены два признака (созданы до кодирования/масштабирования, отдельно
на каждом сыром куске данных — арифметика между колонками одной строки, утечки нет):
- `balance_per_product` — баланс, приходящийся на один продукт клиента
- `balance_per_tenure` — темп накопления баланса относительно стажа обслуживания
  (`balance / (tenure + 1)`)

Также протестирован бинарный признак `has_balance` (флаг наличия ненулевого
баланса) — эмпирически не дал прироста метрик и был исключён из финального
пайплайна.

### Известные ограничения / открытые вопросы

- **`active_member`** — признак потенциально может нести временную утечку (нет
  временных меток, чтобы подтвердить или опровергнуть). Признак оставлен в модели.
  Проверка через SHAP/feature importance — следующая итерация.
- **SHAP-анализ** (полный, по всем признакам) — отложен на следующую итерацию.
- **Деплой** (FastAPI + Docker) — отложен на следующую итерацию.

## Итоги второй итерации: SHAP-анализ

Выполнен SHAP-анализ финальной модели (Random Forest) с помощью `TreeExplainer`
(глобальный `summary_plot` + точечный `dependence_plot` для отдельных признаков).

### Топ признаков по значимости

1. **`age`** — чем старше клиент, тем выше вероятность ухода.
2. **`products_number`** — немонотонная зависимость: клиенты с малым (1) или
   большим (3-4) количеством продуктов чаще уходят из банка, причём эффект
   заметно сильнее выражен у клиентов с 3-4 продуктами. Клиенты со "средним"
   количеством (2) — наиболее стабильный сегмент.
   Можно предположить (доказать или опровергнуть на имеющихся данных нельзя),
   что банк предлагает новым клиентам более выгодные условия, тогда как
   давние клиенты таких бонусов не получают и переходят на более выгодные
   условия к конкурентам. Клиенты с малым количеством продуктов слабее
   "укоренены" в банке и более свободны в выборе других предложений.
3. **`active_member`** — входит в топ-3 по значимости, влияние сопоставимо по
   масштабу с `age` и `products_number`; направление влияния логично с точки
   зрения бизнеса (неактивные клиенты чаще уходят). Прямых доказательств
   утечки не обнаружено. Однако из-за отсутствия временных меток в данных
   нельзя железно исключить, что статус активности зафиксирован постфактум
   (после решения клиента уйти). Признак сохранён в модели как содержательный.

## Итоги третьей итерации: Деплой

Собран единый `sklearn.Pipeline`, объединяющий весь путь от сырых данных до
предсказания: feature engineering (`FunctionTransformer` с функцией
`create_new_features` — добавляет `balance_per_product` и `balance_per_tenure`),
кодирование/масштабирование (`transformer_final`) и финальную модель
(Random Forest). Пайплайн обучен на `train+val`, проверен на воспроизводимость
метрик и сохранён через `joblib`.

Реализован API на **FastAPI** (эндпоинт `POST /predict`), принимающий батч
клиентов и возвращающий вероятность ухода для каждого. `customer_id` не
участвует в предсказании — отделяется перед подачей в модель и "приклеивается"
обратно к результату для идентификации клиента.

Входные данные валидируются через Pydantic (`schemas.py`) с ограничением
допустимых диапазонов (`Field(ge=..., le=...)`) и допустимых категорий
(`Literal` для `country`/`gender`). Диапазоны введены осознанно: Random Forest
в силу своей структуры не экстраполирует — значения за пределами диапазона
обучающих данных не получают содержательного веса и не отражают реальную
картину по клиенту, а API до этого момента пропускал их без предупреждения.

Приложение упаковано в **Docker** (`python:3.11-slim`, слои упорядочены так,
чтобы установка зависимостей кэшировалась отдельно от изменений кода).

### Как запустить

```bash
docker build -t churn-api .
docker run -p 8000:8000 churn-api
```

Пример запроса:

```python
import requests

data = {
    "customers": [
        {
            "customer_id": 101,
            "credit_score": 650,
            "country": "France",
            "gender": "Male",
            "age": 25,
            "tenure": 2,
            "balance": 1500.50,
            "products_number": 2,
            "credit_card": True,
            "active_member": True,
            "estimated_salary": 50000.0,
        }
    ]
}

response = requests.post("http://127.0.0.1:8000/predict", json=data)
print("Статус:", response.status_code)
print("Ответ:", response.json())
```
